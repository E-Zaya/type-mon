# TypeMon アプリ版に向けたメモ

作成: 2026-10-17。Web 版を直しながら気づいた、スマホアプリ（Android IME → iOS）で必要になる設計と、思いついたアイデアの置き場。
Web 版の改善一覧は 2026-10-17 のアイデア一覧（Zaya 作成）を元にしている。思いついたら日付を付けて下に足す。

## 1. 移植の契約（Web 版で既に用意したもの）

- **`lib/transliterate-rules.json` が表の唯一の出典**。TS エンジンはこれを読む。Kotlin / Swift も同じファイルを読むか、ビルド時に埋め込む。表をコードに書き写さない
- **`lib/transliterate-fixtures.json` が合格条件**。全実装がこの `{input, expected}` を全部通すこと。新しいケースは必ずここに足し、プラットフォーム側のテストにだけ書かない
- **`lib/transliterate-exceptions.json` が例外辞書**。キーは `_` なしのラテン、値はキリル。**前方一致**で効く（`batswh` → `batswhiin` も）。そのためキーは語幹で書き、多文字規則の先頭になる文字（i/a/e/o/u/s/t/c/z/y/w/q）で終えない（`batswwr`、`batswwri` ではない）。テストが検査する
- **ユーザー辞書は完全一致のみ**。学習したキーが前方一致すると、誤入力（`s_h` → `sh`→сх）が以後の全語を壊す。接尾辞付きの形は、もう一度 `_` で打てば別途学習される。キーは 3〜40 文字の小文字ラテンに限る
- エンジンの処理順: NFC 正規化 → 単語ごとの ALL CAPS 判定 → 語頭で辞書（ユーザー辞書の完全一致 → 例外辞書の最長前方一致。`_` を含む語は辞書を引かない）→ `_` 区切り → アポストロフィ（ь/ъ） → 多文字表 → 1文字表。この順番を変えると fixture が落ちる

## 2. 設計メモ（アプリ版）

### composing buffer（最優先）
- 現在の単語（Latin）を未確定文字列として持ち、**キーごとに単語全体を `transliterate` し直す**。文字単位の差分変換はしない（`s`→с の後に `h` が来て ш になる、`a`→`aa` など）
- 確定はスペース・句読点・改行。確定時に Latin 側を捨て、Cyrillic だけを本文に commit する
- Backspace は Latin 側の末尾を 1 文字消して再変換（キリル側を消さない）。ユーザーの見た目は「1 文字戻った」になる
- 既存の `transliterate(text)` は純粋関数なので、そのまま毎キー呼べる。単語 1 つなら十分速い

### 候補バー
- `_` を打たせない。`ts` を含む単語を打っている間は候補に「ц」「тс」の両方を出す（例: `untsan` → унцан / унтсан）
- 候補を選んだら、その単語をユーザー辞書に入れる（Web 版の `lib/user-dictionary.ts` と同じ形: `{ latinLower: cyrillicLower }`）
- 候補の優先順位: ユーザー辞書 → 例外辞書 → 機械変換

### キーキャップのヒント
- Q に「Ө」、W に「Ү」、`'` キーを独立させて長押しで `''`（ъ）
- 初回起動のチュートリアルは Web の早見表（`SettingsModal`）と同じ内容にする。説明を 2 箇所で別々に書かない

### オフライン・データ収集なし
- iOS のキーボード拡張は「フルアクセス」なしで動かす。通信を一切しない。変換は端末内で完結
- AI 添削（`/api/polish`）はキーボードには入れない。確定した文章を本体アプリに渡して使う
- ユーザー辞書・学習データは端末内だけ（Web 版は localStorage）

### 逆変換（キリル → ラテン）
- `lib/reverse.ts` に TypeMon 方式と MNS 5217 方式の 2 つを用意した。アプリの共有シート（「ラテンで送る」）に使える

## 3. 気づいたこと・落とし穴

- **Gemini 無料枠は 1 分 10 回**（2026-10-04 に確認）。Web の 1 日 10 回/ブラウザの制限はこれを守らない。アプリで AI 添削を出すなら有料枠か、サーバー側の分あたり制限が先
- **長母音 + i は現状 `aai` → ааи**。モンゴル語に ааи も аай も出てこないので今は固定しただけ。実例が出たら fixture を変える
- `ye` → е / `e` → э は若い人ほど間違える（е を `e` で打つ）。アプリでは候補バーで е/э の両方を出すのが自然
- 人名の `тс`（Батсайхан、Цогтсайхан）は例外辞書より「候補バー + 学習」で解くのが筋。辞書は初期データ
- **ゆるいモードは短い語を触らない**（4 文字未満は対象外）。語彙 251 語では уг→үг、хун→хүн のような誤置換が起きた（2026-10-17 のレビューで実測）。頻度付きの語彙が入るまで実験扱い
- 逆変換で й を `i` にできるのは а/о/у/ү/э/и の後だけ（エンジンに ai/oi/ui/wi/ei/ii しかない）。музей は `muzyey`。アプリの共有シートで逆変換を出すときも同じ表を使う
- 共有カードは Web に 1200×630（OG）と 1080×1920（ストーリー用）がある。アプリの結果画面からも同じ URL を叩けば画像が作れる（`/og/wpm?…`、`/og/wpm/story?…`）

## 4. アイデア（思いついた順）

- 2026-10-17: タイピングゲームの「cy」モードの開始前ヒント（q=ө など）をアプリのチュートリアルに流用する
- 2026-10-17: ユーザー辞書を QR か短い URL で端末間に持ち運べるようにする（アカウント不要のまま）
- 2026-10-17: 候補バーの「ゆるい入力」（o→ө、u→ү の候補）は辞書サイズが鍵。Web の `MN_WORDS` 約 250 語では足りない。頻度付きの語彙リスト（数千語）が要る
